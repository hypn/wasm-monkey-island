- **C17 Kitchen "walks over" stool/table, bottom middle (investigated).** Object 344 'table' (and 342 barrel, 343 pot) have *no OI image*; occlusion comes from the room BM mask plane + box mask byte. Box 0 (mask 1) clips correctly (legs hidden behind stool, verified native render). - **C18 After bar -> kitchen -> back to the dock, can't walk left (camera stuck).** Symptom: dock camera stays at the door (x=361) while ego walks off-screen left. Cause: `eng_follow_actor` set `g_cam_follow=a`, then switched room (EXE `7e3c` -> `2a6e`), and `eng_start_room` resets follow to 0 (EXE `2a6e` sets camera mode 4db1=3). The EXE's `7e3c` sets mode 2 (follow) again *after* the room switch; we did not. (The first dock->bar trip hid it.) Fix: re-assign `g_cam_follow` after the switch. Check: native click script dock->bar->kitchen->bar->dock then click far left: `ego=1 cam=160 follow=1`, ego reaches x~147 (`TRACE_CAM=1` logs setCameraAt/panCamera/followActor with script numbers; `DUMP=1` prints follow).
- **C19 Text drawn as thin 1px font (no outline).** Symptom: "Look at" replies etc. in a thin grey/white 1-pixel font; DOSBox shows thick white text with a black outline. Causes: (1) charset blocks 902/904 are **2 bits per pixel** (header: 15-byte colour map, then bpp, height); we read every glyph as 1 bpp. Pixel value 1 = text colour, value v>=2 = colour map entry v-1 (value 2 = black outline) [EXE `f020` builds colour table 0x2860[v]]. (2) `cursorCommand` sub **13** (not 12) is initCharset (`f020`); sub 12 is a video/palette init, so we never switched from charset 1. Boot script 1 selects charset 2, intro captions use 4. Fix: bpp-aware `cs_draw_char`, charset on sub 13. Check: `TRACE_CS=1` lists `charset N (script, room)`; talk text white with black outline, intro captions still fine, verbs now use charset 2 (verify layout vs DOSBox). Open: EXE keeps a per-text-slot charset (0x7276) and per-actor override (0x3464); we use one global.
- **C20 Verbs drawn in the bold dialogue font.** Cause: one global charset; after C19 the boot script's `initCharset 2` made everything bold. The EXE (and ScummVM `verbs.cpp`) store the charset **per verb**, copied from the current charset when the verb is created (`verbOps` sub 9 "new"). Fix: `VerbSlot.charset` set at creation; draw/erase/hit-test use it. Check: verbs thin (charset 1, created by script 31 before `initCharset 2`), talk text bold.
- **C21 Troll dialog: Guybrush's chosen line not shown.** Symptom: after picking a choice the troll answers but Guybrush says nothing. Cause: the print text is `FF 05 01 40` (verb-name escape whose variable operand is `0x4001` = *local* var 1); `expand_codes` masked the operand with 0x3FF and read a global, yielding an empty string. Fix: `vm_read_var()` honours the bit (0x8000) / local (0x4000) flags (EXE variable addressing). Check: `TRACE_TXT=1` shows `talk actor=1 ... 'Why not?'`; line appears above Guybrush's head. Related: any `FF 04..07 <var>` escape now resolves locals.
- **C22 All talk text white (actor talk colours ignored).** Symptom: troll should be light cyan (11), other actors their own colours. Cause: we used the colour passed by the `print` op (default 15) and only fell back to the actor's talk colour when that was 0. EXE `9a94` does the opposite: for any actor < 0x80 the colour is the actor's talk colour (`0x56ab[actor]`, set by actorOps 0x0e, default 15); the print-op colour/`0x491c` default is used only for non-actor text (actor 0xFF). ScummVM agrees (`_charsetColor = a->_talkColor`). Same routine: an actor not in the current room produces **no text** (we printed it). Fix: `txt_print` slot 0 uses `talk_color` for actors, returns for absent actors. Check: `TRACE_TXT=1` prints `talkColor actor=N color=C`; troll text light cyan in the dock. Why missed: I inferred "colour = print arg, 0 means actor colour" from ScummVM's v5 shape without reading `9a94`; lesson: for text, read 9a94/9b64/98fa fully (still unaudited: wrapping/position/timing).

- **D3 Game ran ~1.4% too fast (music "slightly fast").** Cause: I assumed one game tick = 1/60 s (ScummVM's timer unit). ## G. Reference policy
The game's `MIDEMO.EXE` is the truth we follow. ScummVM's `engines/scumm` is used only to sanity-check behaviour, quirks and known bugs; code is not copied or transliterated from it (an earlier `walk.c` that was too close to the ScummVM structure was discarded and rewritten).

## H. Audit log
* Operand-width audit: `work/audit_ops.py` (B12).
* Behaviour audit (this session): read each handler/helper in the decompile against `engine/*.c`; findings B13-B20 above. Still **not** audited line-by-line: text placement/wrapping (`9a94/9b64/98fa`), palette ops (`roomOps 4`, `ed40`), actor palette (`b414`), flashlight, `0xFF` text codes inside verb names, save/restore.

- **UI1 No way to cancel a verb chosen by hotkey/click.** Added: Esc (while input is enabled) and right-click both re-select the "Walk to" verb (a synthetic click on that verb slot, found by name), so any pending verb is dropped; right-click no longer reaches the room click script. Check: press `T` (sentence "Talk to"), then Esc or right-click -> "Walk to". Verified via the script's current-verb variable (demo var 110, retail var 107) returning to its default.

- **R1 Esc during the retail intro start -> black screen, music stops after a second.** Cause: `beginOverride` remembers (slot, pc) of the script that set it. The copy-protection script set one; we then killed that script, and its slot was reused by the boot script (149). Pressing Esc later jumped that slot to the stale pc, so script 149 ran garbage (`startRoom -2357`). Fix: an override is only valid while its slot still runs the same script (same base and number); otherwise it is forgotten (`override_valid` in `vm.c`). Check: native `STOPSCR=151,152,155,156 KEYS=<f>:27` for f = 10..200 always ends in room 33 with a picture (before: frames 30-45 ended in room 58, black).

- **R2 Retail: `VM error: var oob` / garbage pcs after picking up an object (e.g. "pot", obj 333 in room 41).** Cause: `eng_pickup_object` kept only 64 bytes of the object's code in the inventory slot; retail object code is longer (pot = 105 bytes), so its verb scripts ran past the buffer. Fix: slots hold `INV_OBJ_MAX` (1024) bytes; save format bumped to v2 with migration of v1 saves (see RE_NOTES "Save-game versioning"). Check: `GOTO=41 PICKUP=1350:333` then run a verb on the object from inventory: no VM errors; a v1 save loads with identical inventory code.
- **C23 Sword fight: pirate insults (and any `FF 07` string) not shown.** Symptom: the pirate's lines / insult text were blank. Cause: C21 made all of `FF 04..07 <u16>` read the operand as a *variable*. For `FF 07` the operand is the **string slot itself** (script 82 stores the insult with `stringOps 1, slot 0x18` and prints `FF 07 18 00`); we looked up `g_strings[value of var 24]`. ScummVM's `convertStringMessage` only dereferences the operand for v3 / v6+, not v4/v5. Fix: `expand_codes` in `ui.c` uses the literal operand for code 7 (codes 4/5/6 still read variables). Check: `TXTTEST=1 TRACE_TXT=1 GOTO=41 ./mi_native ../web/retail/ 2002 ...` prints `talk actor=1 ... 'Soon you'll be wearing my sword!'` (string slot 24 set natively, printed via `FF 07 18 00`). Not verified in a real fight (hard to reach natively); please re-test in the browser.
- **C24 Text-escape audit (follow-up to C21/C23).** Root cause of C23: I generalised from one observed case (`FF 05 01 40` = variable operand) to "all of `FF 04..07` take a variable", without reading what each code means. The text escapes are **not** uniform; ScummVM (`convertMessageToString` / `resStrLen` / `convertNameMessage`) is the reference: `FF 01/02/03/08` have no operand; `FF 04` int, `05` verb name, `06` object-or-**actor** name read a *variable*; `07` string uses the operand *as the slot*; `09/0A/0C/0D/0E` carry a 16-bit operand (anim/sound/colour/charset). Same-class problems found and fixed: (1) `FF 06` ignored actors (ids <= numActors are actors, name from actorOps 0x0f); (2) inline script text readers (object names, verb names, `stringOps 1`) always swallowed 3 bytes after any `FF` - a `FF 01` newline would eat the next two bytes (possibly the NUL), while the print reader knew only codes 4..7 had operands - now one shared `fetch_inline_text()` in `vm.c` (rule: operand unless code is 1/2/3/8); (3) codes 9/10/12/13/14 are now dropped with their operand when expanding (not implemented, but the operand was printed as glyphs); `verb_text` skips their 4 bytes. Lesson: before assuming an operand's meaning, find the consumer in ScummVM (or the EXE) per code. `FF 0C <colour>` (ScummVM `handleNextCharsetCode`: set text colour, 0xFF = default) is implemented in `ui.c` (kept internally as `FF 0C hi lo` nibble-encoded so no byte is 0/0xFF; honoured by wrapping, width and drawing, colour persists across wrapped lines). A scan of every retail script/LS/OC/EX/EN found **no** `FF 09/0A/0C/0D/0E` in text, so MI1 never uses them; 9 (anim), 10 (sound), 13 (no-op in ScummVM) and 14 (charset switch) are consumed and ignored. Check: `TXTTEST=c TRACE_TXT=1 GOTO=41 ./mi_native ../web/retail/ 2010 <out> 0` draws "Hello cyan red white ..." in three colours, wrapped.
