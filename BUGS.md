# BUGS.md — bug history and regression checklist

Each entry: **Symptom** → **Cause / wrong assumption** → **Fix** → **Regression check** (how to see it again).
Native test driver: `engine/mi_native <demo dir> <frames> <out-prefix> <dump-every>` with env `CLICKS=frame:x:y:btn,...` (btn 0 = mouse move only; send a move 2-4 frames
before a click so the hover script updates), `GOTO=<room>`, `ENTER=1` (enter the bar via its door), `DUMP=1`, `TRACE*` (see RE_NOTES.md). Browser: `web/test/cdp.js`.
Frame numbers below are approximate (dock scene starts ~frame 700).

## A. Data / format assumptions

| # | Symptom | Cause (wrong assumption) | Fix | Regression check |
|---|---|---|---|---|
| A1 | Index directories parsed as garbage (counts like 65436) | Assumed the whole `000.LFL` payload was XOR 0xFF; only the room *names* are | Directories are plain: `u16 n`, then `n × {u8 room, u32 off}` (5 bytes each) | `t_res`-style load: scripts 1..100 all resolve to an `SC` block |
| A2 | Text drawn as scrambled dots | Glyph bitmaps assumed row-padded to bytes | Glyph bits are one continuous stream (`bit = row*w + col`) | Boot: "Guybrush Threepwood" caption is legible |
| A3 | Costume decode read past the data / crashed | Offsets assumed relative to the data *after* the 6-byte block header | All costume offsets are relative to the block start (header included) | Room 3 (logo) → dock transition runs without ASAN errors; costume 2 pictures are 2x1, 6x5, 8x7… |
| A4 | Verbs parsed with shifted operands (huge variable numbers, "var oob") | `verbOps` sub-op 9 (*new*) was given a parameter byte; it has none | Sub-op 9 takes no argument | Boot script 31: verbs Open/Close/Push/Pull appear at the right places, no `VM error` lines |
| A5 | Verb panel ended at the wrong row / room drawn at y=0 | `roomOps 3` args read as (top, bottom) | They are (top, **height**): main view top=16, height=144 | Verb rows at y≈152..184, room image starts at screen row 16 |
| A6 | Verb with id 0 (the sentence line) never drew | Slot id 0 used as the "empty slot" marker | Separate `used` flag per verb slot | Hover a door: "Walk to door"/"Open door" appears centred under the room |

- **C16 Bar-entry head looks "up" / default head wrong after walking in.** Symptom: entering the SCUMM Bar Guybrush's body faces right but his head faces away; walking up/down "fixes" it. Cause: `eng_load_room_with_ego` assigned `ego->facing` directly, bypassing the limb redirect (`act_set_facing` -> `redirect_limbs`, EXE `ceae`/`d12e`), so limb frames kept the old direction. Fix: use `act_set_facing(ego, (eng_obj_walk_dir(obj)^1)&3)`. Check: `CHECK_LIMBS=1` env logs `LIMB MISMATCH` whenever a stopped actor has a limb frame whose dir != facing (clean after fix).
- **C17 Kitchen "walks over" stool/table, bottom middle (investigated).** Object 344 'table' (and 342 barrel, 343 pot) have *no OI image*; occlusion comes from the room BM mask plane + box mask byte. Box 0 (mask 1) clips correctly (legs hidden behind stool, verified native render). EXE `b9b2` switches the actor's current box (and mask via `ca48` -> `[0x1556+actor]`) only once the position is inside the next box, as ours does; boxes 1/2/5 have mask 0 by data, so the sprite edge can overlap 1-3px of the stool when standing at the box edge (x<=109). No EXE rule found that differs; not changed. Earlier `dist` build lacked the mask plane/facing fixes -> rebuilt. Re-test in browser; if still wrong, report the exact spot.
- **C18 After bar -> kitchen -> back to the dock, can't walk left (camera stuck).** Symptom: dock camera stays at the door (x=361) while ego walks off-screen left. Cause: `eng_follow_actor` set `g_cam_follow=a`, then switched room (EXE `7e3c` -> `2a6e`), and `eng_start_room` resets follow to 0 (EXE `2a6e` sets camera mode 4db1=3). The EXE's `7e3c` sets mode 2 (follow) again *after* the room switch; we did not. (The first dock->bar trip hid it.) Fix: re-assign `g_cam_follow` after the switch. Check: native click script dock->bar->kitchen->bar->dock then click far left: `ego=1 cam=160 follow=1`, ego reaches x~147 (`TRACE_CAM=1` logs setCameraAt/panCamera/followActor with script numbers; `DUMP=1` prints follow).
- **C19 Text drawn as thin 1px font (no outline).** Symptom: "Look at" replies etc. in a thin grey/white 1-pixel font; DOSBox shows thick white text with a black outline. Causes: (1) charset blocks 902/904 are **2 bits per pixel** (header: 15-byte colour map, then bpp, height); we read every glyph as 1 bpp. Pixel value 1 = text colour, value v>=2 = colour map entry v-1 (value 2 = black outline) [EXE `f020` builds colour table 0x2860[v]]. (2) `cursorCommand` sub **13** (not 12) is initCharset (`f020`); sub 12 is a video/palette init, so we never switched from charset 1. Boot script 1 selects charset 2, intro captions use 4. Fix: bpp-aware `cs_draw_char`, charset on sub 13. Check: `TRACE_CS=1` lists `charset N (script, room)`; talk text white with black outline, intro captions still fine, verbs now use charset 2 (verify layout vs DOSBox). Open: EXE keeps a per-text-slot charset (0x7276) and per-actor override (0x3464); we use one global.
- **C20 Verbs drawn in the bold dialogue font.** Cause: one global charset; after C19 the boot script's `initCharset 2` made everything bold. The EXE (and ScummVM `verbs.cpp`) store the charset **per verb**, copied from the current charset when the verb is created (`verbOps` sub 9 "new"). Fix: `VerbSlot.charset` set at creation; draw/erase/hit-test use it. Check: verbs thin (charset 1, created by script 31 before `initCharset 2`), talk text bold.
- **C21 Troll dialog: Guybrush's chosen line not shown.** Symptom: after picking a choice the troll answers but Guybrush says nothing. Cause: the print text is `FF 05 01 40` (verb-name escape whose variable operand is `0x4001` = *local* var 1); `expand_codes` masked the operand with 0x3FF and read a global, yielding an empty string. Fix: `vm_read_var()` honours the bit (0x8000) / local (0x4000) flags (EXE variable addressing). Check: `TRACE_TXT=1` shows `talk actor=1 ... 'Why not?'`; line appears above Guybrush's head. Related: any `FF 04..07 <var>` escape now resolves locals.
- **C22 All talk text white (actor talk colours ignored).** Symptom: troll should be light cyan (11), other actors their own colours. Cause: we used the colour passed by the `print` op (default 15) and only fell back to the actor's talk colour when that was 0. EXE `9a94` does the opposite: for any actor < 0x80 the colour is the actor's talk colour (`0x56ab[actor]`, set by actorOps 0x0e, default 15); the print-op colour/`0x491c` default is used only for non-actor text (actor 0xFF). ScummVM agrees (`_charsetColor = a->_talkColor`). Same routine: an actor not in the current room produces **no text** (we printed it). Fix: `txt_print` slot 0 uses `talk_color` for actors, returns for absent actors. Check: `TRACE_TXT=1` prints `talkColor actor=N color=C`; troll text light cyan in the dock. Why missed: I inferred "colour = print arg, 0 means actor colour" from ScummVM's v5 shape without reading `9a94`; lesson: for text, read 9a94/9b64/98fa fully (still unaudited: wrapping/position/timing).

## E. Known open items (not bugs fixed yet)

* Exit-script actor kill (B2) is worked around, not explained.
* Walking is straight-line + snapping, not the original box-matrix path walker (`FUN_1000_b600` family); scaling slots (`SA` block) unused.
* No sound/music; AdLib/PC-speaker resources (`0N`) are ignored.
* The DOSBox-X oracle (`work/oracle/run.sh`) could not be used past the intro (crash/black frames), so dock/bar behaviour was checked against the script logic and user reports.

## F. Suggested automated regression set

1. `ENTER=1` + scripted clicks above (B5/B8/C6): assert `room`, ego position and `facing` from `DUMP=1`.
2. Frame hash/diff of the headshot intro frame (A2/B10) against the stored DOSBox-X comparison (99.2% match baseline).
3. `mi_asan` build (`-fsanitize=address,undefined`) over 3000 frames of the intro + dock (A3).
4. `web/test/cdp.js` smoke test: page loads from `file://`, `window.__frames` increases, room reaches 55.

## G. Reference policy
The game's `MIDEMO.EXE` is the truth we follow. ScummVM's `engines/scumm` is used only to sanity-check behaviour, quirks and known bugs; code is not copied or transliterated from it (an earlier `walk.c` that was too close to the ScummVM structure was discarded and rewritten).
